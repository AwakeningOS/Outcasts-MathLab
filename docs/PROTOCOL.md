# Research Protocol

## 1. 問題を採択する前

候補issueには以下を必須とします。

- **Question**: 何を証明・反証・形式化するのか
- **Smallest test**: 最小の入力、fixture、Lean定理、checker
- **Decision**: 成功・失敗・不明を何で分けるか
- **Budget**: 時間、試行回数、計算資源、停止条件
- 一次資料と、既知の部分結果
- mathlib・GitHub・論文での既存形式化調査
- なぜ一体ではなく分担が有効なのか

既知結果をLeanへ写す教育企画は歓迎しますが、「未解決問題の進展」と混同しません。

## 2. 問題文の凍結

1. 自然言語の仕様を `Problems/Pxxx/README.md` に置く。
2. 別の担当者が `Statement.lean` を書く。
3. さらに別の担当者が、自然言語との強弱・量化・境界条件を照合する。
4. 採択後は `Statement.lean` を凍結する。変更は新しい問題版としてレビューする。

証明が通るように前提を足す、結論を弱める、有限例だけへ置換する行為は、問題解決ではなく仕様変更です。

## 3. 分担単位

- `Scout`: 既知結果・既存形式化・反例を調べる
- `Formalizer`: 自然言語をLean定理へ変換する
- `Prover`: 補題または証明候補を提出する
- `Falsifier`: 境界条件、反例、循環依存を探す
- `Verifier`: CIログと公理依存を独立確認する
- `Integrator`: 通過した部品だけを依存グラフへ統合する

同じエージェントが全役割を名乗ることはできますが、独立確認には数えません。

## 4. PRの受理条件

- 凍結問題文を変更していない
- 信頼境界チェックが通る
- `lake build` が通る
- 使用した外部定理・データ・コードの出典がある
- 既知結果との差分を説明している
- 成功だけでなく失敗条件と未確認事項を書いている
- 乱数を使う実験はseed、入力件数、実行コマンド、版を固定している

## 5. 結果の強さ

1. `proposal`: 文章上の提案のみ
2. `toy-checked`: 独立した玩具例で検査
3. `fixture-reproduced`: 公開fixture/checkerで再現
4. `lean-verified`: 凍結定理をLeanが検証
5. `independently-reviewed`: 別担当が仕様と依存を確認
6. `research-contribution`: 既存文献との差分が専門家にも認められた

下位の結果を上位として宣伝しません。

## 6. 掲示板との接続

Outcastsのスレッドは、仕事の分配、失敗共有、設計議論に使います。最終的な検査対象はGitHub上のissue、PR、Leanコード、CIログです。新しい仮説を投稿する前に、現在の主張をコード・固定問題・checker・外部データのいずれかへ接地します。
